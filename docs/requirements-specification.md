# 多聊天室群聊系统需求分析

> 本文基于《多聊天室群聊系统架构设计》及已确认的补充规则整理。聊天室生命周期、消息顺序、逻辑删除后的访问、审核配置、留存和 WebSocket 会话的实现，必须以 [《多聊天室群聊业务规则与状态机》](business-rules-state-machine.md) 为准；如有不一致，以该规范为准。

## 1. 系统目标与范围

系统面向投研投顾直播间，提供多聊天室实时群聊能力，并确保普通用户消息经过审核、管理员操作可追溯、断线消息可恢复。

系统应支持：

- 多聊天室独立运营与管理员分级管理。
- 用户加入、退出和审批入群。
- WebSocket 实时通信与历史消息查询。
- 普通消息审核、批量审核与审核超时。
- 管理员普通消息、跨房间广播和紧急通知。
- Redis 缓存、限流和审核超时调度。
- PostgreSQL 事务一致性与审计。
- 默认保留 3 个月历史消息。

系统不支持图片、文件、附件、复杂报表、微服务治理或完整 RBAC 平台。

## 2. 角色与权限

| 角色 | 功能范围 |
| --- | --- |
| `USER` | 注册、登录、浏览房间、申请加入、退出、发送消息、查看个人消息状态与已发布历史 |
| `ROOM_ADMIN` | 管理授权房间、审批入群申请、审核消息、发送普通管理员消息和紧急通知 |
| `SYSTEM_ADMIN` | 管理全部房间和权限范围、全局审核、跨房间广播、查看系统审计与指标 |

服务端必须基于 JWT、成员关系和管理员房间授权重新校验权限，不能信任前端传递的用户 ID、角色或房间权限。

## 3. 聊天室与成员管理

### 3.1 聊天室

聊天室包含名称、描述、最大人数、加入方式、状态和创建人等信息，支持名称、状态、加入方式及分页筛选。

| 状态 | 用户加入 | 普通用户消息 | 管理员普通消息 | 紧急通知 | 历史消息 |
| --- | --- | --- | --- | --- | --- |
| `ACTIVE` | 允许 | 允许，需审核 | 允许 | 允许 | 可查 |
| `PAUSED` | 不允许 | 不允许 | 允许 | 允许 | 可查 |
| `CLOSED` | 不允许 | 不允许 | 允许 | 允许 | 可查 |
| 已删除 | 不允许 | 不允许 | 不允许 | 不允许 | 按审计权限查询 |

- 删除采用逻辑删除，保留房间、成员、消息和审计关联数据。
- 房间管理员仅能管理被授权的房间。

### 3.2 加入与退出

- `OPEN` 房间：校验人数后直接加入。
- `APPROVAL` 房间：用户申请后进入 `PENDING`，管理员批准后成为 `ACTIVE`。
- 申请不占用房间名额；批准时再次校验人数上限。
- 并发加入或批准时，必须通过数据库事务和行锁避免超额。
- 用户退出后状态变为 `EXITED`，并取消实时订阅。
- 再次申请必须新建申请记录，保留历史；同一用户、同一房间同时最多一条 `PENDING` 或 `ACTIVE` 记录。

## 4. 消息与审核

### 4.1 消息规则

- 仅支持文本消息，不支持图片、附件和文件。
- 单条文本最多 320 个 Unicode 字符。
- 用户必须是有效成员，且房间为 `ACTIVE` 才可发送普通消息。
- 服务端需校验空文本、长度、成员资格、房间状态、敏感词和发送频率。
- 用户默认限流：每秒最多 2 条、每分钟最多 20 条；超限消息不入库、不进入审核队列。

### 4.2 消息类型与状态

| 消息类型 | 发送者 | 审核 | 展示方式 |
| --- | --- | --- | --- |
| `CHAT` | 普通用户 | 必须 | 审核通过后发布 |
| `ADMIN_MESSAGE` | 管理员 | 不需要 | 直接进入发布流程 |
| `SYSTEM_NOTIFICATION` | 有权限管理员 | 不需要 | 高优先级、优先展示 |

```text
PENDING_REVIEW → APPROVED → PUBLISHED
                ├→ REJECTED
                └→ TIMEOUT
```

- 当前不要求填写或展示拒绝原因。
- 用户可查询自己的消息内容、房间、提交时间和审核状态。
- 普通用户只能查询房间内已发布的消息。
- 管理员可按房间、用户、状态、时间范围查询审核列表，并支持单条和批量审核。

### 4.3 敏感词策略

敏感词检测必须在服务端执行，词库与规则应可配置。默认建议为：命中敏感词后拒绝提交，不写入消息表、不进入审核队列，并向用户返回统一提示；不暴露具体命中的词。

## 5. 顺序、优先级与可靠性

- 每个房间维护单调递增的 `room_seq`。
- 普通用户消息按提交顺序展示，不能因后序消息先审核通过而乱序。
- 前序消息被拒绝或超时后，可跳过并继续发布后序已批准消息。
- 管理员普通消息无需审核，但应纳入房间消息序列。
- 紧急通知高优先级展示，不受普通消息审核队列阻塞，客户端应置顶或显著提示。
- 推送采用至少一次语义：若审核已通过但 WebSocket 推送失败，消息保持待发布状态，由补偿任务重新推送。
- 客户端必须按 `messageId` 去重。
- 客户端重试同一个提交请求时，应使用 `requestId` 幂等处理，避免创建重复消息。

## 6. 广播与通知

- 管理员可向一个或多个有权限的聊天室广播。
- 每个房间生成独立的 `messageId` 和 `room_seq`。
- 广播允许部分成功，接口必须按房间返回成功、无权限、房间不可发送、推送待补偿等结果。
- 广播或通知的推送失败可由补偿任务后续重试。
- 紧急通知即使绕过审核，也必须持久化并记录审计日志。

## 7. WebSocket 与消息恢复

- 单用户维护一条 WebSocket 连接，可同时订阅多个聊天室。
- WebSocket 建连携带 JWT；订阅时再次验证房间和成员资格。
- 支持订阅、取消订阅、消息提交、聊天推送、审核状态通知、紧急通知和错误通知。
- 向用户提供个人通道，用于审核通过、拒绝、超时等私有状态通知。
- 使用 Ping/Pong 清理失效连接。
- 断线重连后，客户端携带每个房间的 `lastMessageSeq`，服务端补发后续已发布消息。

当前设计的 WebSocket 会话保存在单实例内存中，因此本期以单实例部署满足目标。未来多节点扩容时，需要补充跨节点推送与会话路由方案。

## 8. 数据、一致性与留存

- PostgreSQL 是用户、房间、成员、消息、审核状态、权限和审计的最终数据源。
- Redis 仅存储在线状态、房间缓存、限流和待审核消息超时索引。
- Redis 故障不应造成业务数据丢失；待审核 ZSet 应支持根据数据库中 `PENDING_REVIEW` 消息重建。
- 审核结果与审计日志、入群批准与人数校验必须在同一数据库事务内完成。
- 消息历史默认保留 3 个月，届时执行归档或清理；审计日志保留时间应单独确认，建议长于消息正文。
- 房间缓存采用 Cache Aside，房间更新、关闭或删除后删除缓存。

## 9. 审计、监控与可运维性

审计范围至少包括：

- 登录、加入、退出。
- 入群批准与拒绝。
- 消息提交、批准、拒绝、超时。
- 房间创建、修改、删除。
- 管理员广播与紧急通知。

系统应提供：

- 健康检查。
- 当前 WebSocket 连接数。
- 待审核消息数、审核超时数。
- 当日消息总量、审核耗时、推送失败数。
- 数据库连接池与接口错误率等基础指标。
- 包含 `requestId`、用户、房间和消息标识的业务日志，支持按 `messageId` 追踪完整生命周期。

## 10. 验收重点

- 并发加入最后一个名额时，最多一人成功。
- 非成员、暂停/关闭房间中的普通用户均无法发送消息。
- 普通用户消息审核通过前，其他用户不可见。
- 审核与超时并发时，只能一个状态变更成功。
- 同一房间普通消息严格按提交顺序发布。
- 紧急通知可以优先展示，不被待审核消息阻塞。
- 广播可部分成功，失败房间可进入补偿。
- 重连后能补回漏收消息，重复推送不会重复展示。
- 敏感词和限流消息不进入审核队列。
- 历史消息默认按 3 个月留存策略处理。
- 核心业务单元测试覆盖率不低于 80%。
