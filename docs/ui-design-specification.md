# 多聊天室群聊系统 UI 设计规范与详细设计

> 版本：1.0  
> 设计依据：[需求分析](requirements-specification.md)、[业务规则与状态机](business-rules-state-machine.md) 与 [API / WebSocket 契约](api-contract.md)。其中状态机规则优先级最高。

## 1. 设计目标与边界

本设计服务于投研投顾直播间的实时群聊，包含用户端和管理端。界面必须让用户一眼分清「已公开消息」「我正在等待审核的消息」和「紧急通知」，避免将审核通过但尚受前序消息阻塞的内容误认为已经发布。

- 支持桌面端优先，最小可用宽度为 360px；聊天操作在移动端仍可完成。
- 仅承载文本内容；不出现图片、附件、表情包上传或富文本编辑器入口。
- 管理员能力按 `ROOM_ADMIN` 与 `SYSTEM_ADMIN` 动态显隐；前端显隐仅改善体验，实际权限始终以服务端响应为准。
- 不设计复杂报表。系统指标采用简洁的数值卡片和状态提示。

## 2. 信息架构与导航

### 2.1 角色入口

| 角色 | 主导航 | 默认落点 | 可见的管理能力 |
| --- | --- | --- | --- |
| `USER` | 发现聊天室、我的房间、我的消息 | 发现聊天室 | 无 |
| `ROOM_ADMIN` | 用户端导航 + 管理工作台 | 管理工作台（若有待办）或发现聊天室 | 仅获授权房间的房间运营、入群审批、消息审核、广播与房间审计 |
| `SYSTEM_ADMIN` | 用户端导航 + 管理工作台 | 管理工作台 | 全部管理能力、房间创建/删除、管理员授权、全局审计、运行指标、删除房间取证 |

桌面端使用左侧固定导航（宽 232px）；内容区顶部使用全局栏。移动端将主导航收进抽屉，当前页面标题留在顶部。管理员进入“管理工作台”后使用二级侧栏；不要把管理操作塞入用户端聊天页面。

```text
应用壳
├─ 发现聊天室                 /rooms
├─ 我的房间                   /my-rooms
├─ 我的消息                   /my-messages
└─ 管理工作台（按角色显示）    /admin
   ├─ 房间管理                /admin/rooms
   ├─ 入群审批                /admin/join-requests
   ├─ 内容审核                /admin/reviews
   ├─ 广播与紧急通知           /admin/publish
   ├─ 管理员授权（系统管理员）  /admin/authorizations
   ├─ 审计日志                /admin/audit-logs
   ├─ 已删除房间取证（系统管理员）/admin/forensics
   └─ 运行状态（系统管理员）    /admin/metrics
```

### 2.2 全局栏

左侧为产品标识“研聊”，中部在桌面端保留当前位置面包屑，右侧依次为 WebSocket 连接状态、用户头像/显示名和账号菜单。账号菜单含“个人资料（仅展示）”与“退出登录”。

连接状态只使用圆点 + 简短文案：`实时已连接`、`正在重连…`、`离线，消息可能延迟`。不把技术性连接错误直接暴露给普通用户；状态变为已连接后显示一次轻量提示“实时连接已恢复”。

## 3. 视觉与组件规范

### 3.1 设计语言

整体采用克制、信息密度适中的金融工作台风格：大面积暖灰白背景，深蓝作为操作色，琥珀色仅用于需要用户注意的审核状态，红色严格用于拒绝、删除和紧急通知。避免聊天产品常见的大面积渐变与娱乐化装饰。

| Token | 值 | 用途 |
| --- | --- | --- |
| `--color-primary` | `#2457D6` | 主按钮、链接、选中导航、自己的公开消息气泡 |
| `--color-success` | `#16805C` | 已发布、已加入、系统正常 |
| `--color-warning` | `#B7791F` | 待审核、已批准待发布、房间暂停 |
| `--color-danger` | `#C23934` | 拒绝、超时、删除、紧急通知 |
| `--color-info` | `#667085` | 次级文字、离线、关闭状态 |
| `--surface-page` | `#F6F7F9` | 页面背景 |
| `--surface-card` | `#FFFFFF` | 卡片、面板、对话框 |
| `--border-subtle` | `#E4E7EC` | 分隔线和输入框边框 |
| `--text-primary` | `#182230` | 标题和正文 |
| `--text-secondary` | `#667085` | 辅助信息 |

- 字体：`Inter, PingFang SC, Microsoft YaHei, sans-serif`；正文 14px / 22px，表格 13px / 20px，页面标题 24px / 32px。
- 采用 8px 间距基准：组件内边距 12/16/20/24px，区块间距 24px，页面外边距桌面 32px、平板 24px、手机 16px。
- 圆角：输入和小型控件 8px，卡片 12px，对话框 16px。阴影仅用于悬浮层；内容卡片以边框区分。
- 图标使用单一线性图标库（Element Plus Icons），尺寸 16px/20px；有文字的高风险按钮仍须保留文字，不能仅用图标。

### 3.2 通用控件

| 组件 | 规则 |
| --- | --- |
| 按钮 | 主按钮用于当前页面唯一主动作；次要动作用描边；危险操作使用文字“删除/拒绝/发送紧急通知”，不能只写“确认”。提交中保持按钮宽度并显示加载态，防止重复提交。 |
| 表格 | 表头固定、行高 52px；横向内容在小屏改为卡片列表，不用强制横向滚动完成核心操作。批量选择列仅在审核列表出现。 |
| 筛选器 | 默认展示最常用的房间、状态、时间；其余筛选收进“更多筛选”。筛选变更后重置游标并回到首屏。 |
| 标签 | 状态必须有文字，不只用颜色；遵循第 4 节映射。 |
| 空状态 | 图标 + 一句事实 + 可行动按钮，例如“尚未加入任何聊天室 / 去发现聊天室”。避免用“暂无数据”作为唯一内容。 |
| Toast | 成功 3 秒自动关闭；失败保持 6 秒并含可执行建议。涉及多房间结果时不用单一 Toast 替代结果面板。 |
| 确认对话框 | 用于退出房间、关闭、删除、拒绝、批量审核、发送紧急通知。正文说明不可逆后果；删除需额外输入房间名称确认。 |

## 4. 状态的视觉表达与文案

### 4.1 房间与成员

| 数据状态 | 标签/颜色 | 用户端行为 | 管理端行为 |
| --- | --- | --- | --- |
| `ACTIVE` | 进行中 / 绿色 | 可加入、成员可发言 | 可暂停或关闭 |
| `PAUSED` | 已暂停 / 琥珀色 | 不可加入、输入框禁用；历史仍可查看 | 可恢复或关闭；仍可发管理员消息/紧急通知 |
| `CLOSED` | 已关闭 / 灰色 | 不可加入、输入框禁用；历史仍可查看 | 不可恢复；仍可发管理员消息/紧急通知 |
| `DELETED` | 已删除 / 红灰色 | 从常规列表移除；在“我的消息”仅显示“房间已删除” | 仅系统管理员在取证页查看，只读 |
| `PENDING` 成员 | 已申请，等待审批 / 琥珀色 | 房间详情不可进入聊天，显示撤回不可用（本期无此接口） | 审批队列可批准或拒绝 |
| `ACTIVE` 成员 | 已加入 / 绿色 | 可进入、订阅和发送 | 可查看成员 |
| `REJECTED` / `EXITED` | 未通过 / 已退出 / 灰色 | 可重新申请（会产生新记录） | 仅历史/管理记录展示 |

### 4.2 消息状态

| 状态 | 仅谁可见 | 视觉与固定文案 | 交互要求 |
| --- | --- | --- | --- |
| `PENDING_REVIEW` | 发送者、授权管理员 | 琥珀色“审核中”；发送者消息气泡半透明 | 展示“预计在 HH:mm 前处理”，不出现在公共消息流 |
| `APPROVED` | 发送者、授权管理员 | 蓝灰色“审核已通过，等待按序发布” | 明确不能表述为“已发送”；无需重发 |
| `PUBLISHED` | 房间成员、授权管理员 | 无状态标签或绿色“已发布”（仅我的消息页） | 进入普通消息流，按 `roomSeq` 升序渲染 |
| `REJECTED` | 发送者、授权管理员 | 红灰色“未通过审核” | 不显示拒绝原因；可重新编辑后另发 |
| `TIMEOUT` | 发送者、授权管理员 | 灰色“审核超时，未发布” | 可复制内容后重新发送 |
| `CANCELLED_BY_ROOM_DELETION` | 发送者、可取证管理员 | 灰色“房间已删除，消息未发布” | 禁止重试和跳转房间 |
| `SYSTEM_NOTIFICATION` | 房间成员、授权管理员 | 红色顶部紧急横幅，带“紧急通知”文字与时间 | 独立于普通消息流；按 `notificationSeq` 去重 |

## 5. 详细页面设计

### 5.1 登录与注册 `/login`、`/register`

使用居中的 420px 表单卡片，左侧（宽度 ≥ 1024px）可显示产品价值说明“实时讨论，合规可追溯”，小屏只保留表单。

- 登录字段：用户名、密码；主按钮“登录”；底部链接“没有账号？注册”。
- 注册字段：用户名、显示名称、密码、确认密码；每个字段在离焦后校验。用户名提示 `3–32 位，支持字母、数字、_、-`，密码提示 `8–72 位`。
- 登录失败在密码项下显示“用户名或密码不正确”，不指出具体错误字段。登录成功后读取用户角色并路由至上次访问页或默认页面。
- 令牌失效时保留当前页面意图；刷新失败后跳转登录页，展示“登录已过期，请重新登录”。

### 5.2 发现聊天室 `/rooms`

页面标题“发现聊天室”，右上角仅 `SYSTEM_ADMIN` 看见“新建聊天室”。顶部筛选条由搜索框（名称前缀）、加入方式下拉和状态下拉构成；普通用户默认只看 `ACTIVE`，管理员如需查看非活动房间需主动切换状态。

房间采用两列卡片（≥1280px）、单列卡片（<768px）。卡片包含名称、描述（两行截断）、`进行中/已暂停/已关闭` 标签、`公开加入/需要审批` 标签、`120 / 500 人`容量与创建时间。底部动作依身份变化：

- 未加入 + `ACTIVE`：`OPEN` 显示“加入聊天室”，`APPROVAL` 显示“申请加入”。
- `PENDING`：显示禁用按钮“等待审批”。
- `ACTIVE` 成员：显示主按钮“进入聊天室”。
- 满员/暂停/关闭：按钮禁用，并在按钮旁给出原因。

点击加入后按钮进入加载态；服务端返回 `ROOM_FULL` 等精确错误时就地显示对应文案并刷新卡片数据。使用游标分页的“加载更多”，不使用伪总页数。

### 5.3 我的房间 `/my-rooms`

使用标签页：`已加入`（默认）、`审批中`、`历史记录`（已退出/被拒绝）。每行展示房间摘要、成员状态、加入/申请时间及主动作。

- 已加入：`进入聊天室`、次操作“退出房间”。退出需确认：“退出后将停止接收此房间实时消息；可再次申请加入。”
- 审批中：显示申请时间与“等待管理员审批”，不提供发送或订阅入口。
- 历史记录：已退出和被拒绝记录只展示事实与“重新申请”（前往房间详情）；不会复用旧申请。

### 5.4 聊天室 `/rooms/:roomId/chat`

这是用户端核心页面。桌面为三栏布局：左侧房间切换栏 240px、中部消息区自适应、右侧成员栏 280px；在 1024px 以下隐藏左栏和右栏到抽屉，保留主消息区。

```text
┌ 房间列表 ┬──────────────────── 聊天室：A 股直播间 / [进行中] ───────────────────┬ 成员 120 ┐
│ 搜索房间 │ [紧急通知] 交易时段调整，请留意公告。                         10:32  │ 在线成员 │
│ · A 股   ├───────────────────────────────────────────────────────────────────┤ · 小陈   │
│ · 宏观   │ 10:30  小王   今天市场怎么看？                                  │ · ...    │
│ · 债券   │ 10:31  管理员  今日直播将在 15:00 开始                          │           │
│          │ 10:32  我      关注成交量变化                         [审核中]   │           │
│          ├───────────────────────────────────────────────────────────────────┤           │
│          │ 输入消息…                                             0 / 320     │           │
│          │ 审核通过后才会对其他成员可见。                         [发送]     │           │
└──────────┴───────────────────────────────────────────────────────────────────┴───────────┘
```

**头部。** 显示房间名称、状态、人数、加入方式与描述摘要。操作包括“成员”“历史通知”“更多”。成员可见“退出房间”；授权管理员可见“进入管理”。已暂停/关闭时出现整行提示：`此房间已暂停，不能发送普通消息；历史消息仍可查看。` 或 `此房间已关闭，不能发送普通消息。`

**紧急通知层。** 置于消息列表上方，不混入普通消息。新通知立即展开红色横幅，含内容、发送时间、关闭按钮和“查看全部”入口；用户关闭仅表示本地折叠，不能删除通知。通知抽屉按时间倒序，支持历史分页。

**普通消息流。** 初始历史以 `roomSeq` 倒序拉取，渲染时反转为升序；向上滚动加载更早历史。WebSocket 到达和补偿消息均先按 `messageId` 去重，再按 `roomSeq` 插入。用户处于底部时自动跟随；离底部超过 120px 时不强制滚动，显示“有 N 条新消息，点击查看”。管理员普通消息使用带“管理员”标记的消息头，但仍按普通流顺序排列。

**我的待审浮层。** 消息列表底部上方固定一个仅自己可见的“我的消息状态”折叠面板，最多展示最近 3 条非 `PUBLISHED` 内容；展开可看全部，并跳转“我的消息”。这能避免把待审内容错误插进公共时间线。

**输入区。** 使用 3–5 行自适应文本框，右下显示 `Array.from(content).length / 320`。超过 320 或全空白时禁用发送；按 `Ctrl/⌘ + Enter` 发送，Enter 换行。发送成功立即清空输入，消息只加入“我的消息状态”，并写入本地待发送/待审缓存。敏感词、限流、房间状态或成员权限错误不清空草稿，显示统一错误文案及重试建议。房间非 `ACTIVE` 或用户不再是成员时禁用输入框并说明原因。

**断线和补偿。** 重新连接后为每房间分别携带最近的普通消息和通知游标。收到 `SUBSCRIBED_WITH_GAP` 时显示非阻塞横幅：`部分实时消息已超出留存期，无法补回。`；不伪造缺失内容。收到 `SESSION_REPLACED`/关闭码 `4001` 时停止自动重连，显示“此账号已在其他设备继续使用”，提供“重新登录”按钮。收到房间删除/订阅撤销错误时清空该房间本地订阅和输入状态，返回“我的房间”。

### 5.5 我的消息 `/my-messages`

该页是用户查询审核状态的唯一完整入口。顶部筛选包含房间、状态、类型和时间范围；结果采用消息卡片而非聊天流，每张卡显示内容、房间名/“房间已删除”、提交时间、状态标签及审核截止时间（待审时）。

- `PENDING_REVIEW` 显示倒计时或“截至 HH:mm”；到期后由服务端事件/刷新变为超时。
- `APPROVED` 固定显示“审核已通过，正等待前序消息发布”，不可显示为公共可见。
- 已删除房间的记录不可跳转，房间名称旁显示“已删除”。
- 卡片操作仅有“复制内容”；对非发布状态可提供“重新发送”预填聊天草稿，但必须生成一条新消息，不能复用原 `requestId`。

### 5.6 管理工作台 `/admin`

默认页不是复杂仪表盘，而是“待办优先”的工作台：第一行显示 `待审批入群`、`待审核消息`、`今日审核超时` 三张可点击统计卡；`ROOM_ADMIN` 只看已授权房间数据，`SYSTEM_ADMIN` 可增加 `推送待补偿` 卡。下方是“最早待处理消息”五行预览和“最近房间状态变更”。

若接口尚未提供聚合待办数据，前端分别请求现有审批、审核列表并只显示可访问房间的首屏数量；不虚构统计口径。

### 5.7 房间管理 `/admin/rooms` 与详情抽屉

表格列：房间名称、状态、加入方式、成员数/上限、创建时间、最后更新、操作。筛选：名称、状态、加入方式。`SYSTEM_ADMIN` 有“新建聊天室”；新建弹窗字段为名称、描述、最大人数、加入方式，创建后初始状态固定为 `ACTIVE`，不提供草稿按钮。

点击行打开详情抽屉，分为“基本信息 / 成员 / 房间审计 / 管理员授权（仅系统管理员）”。编辑遵循可达状态：

- `ACTIVE`：可“暂停”“关闭”；
- `PAUSED`：可“恢复”“关闭”；
- `CLOSED`：状态控件锁定并说明“已关闭的房间不能重新开启”；
- 删除只对系统管理员显示在危险操作区。点击后需输入完整房间名称，且文案明确“所有未发布普通消息将被取消；此操作不能恢复”。

成员标签展示“当前成员”，管理员可切换到全部状态。成员普通展示字段仅为显示名、加入时间、状态，避免在用户端暴露不必要身份信息。

### 5.8 入群审批 `/admin/join-requests`

默认筛选为“待审批”，按申请时间正序，保证先到先处理。表格列为申请人、房间、申请时间、当前成员/上限、操作；房间管理员的房间选择器仅加载授权范围。

单行“批准”使用主按钮，“拒绝”使用文字危险按钮。批准前二次确认不必重复确认，除非剩余席位为 1：此时提示“批准时将再次校验容量，可能因并发操作失败”。批量审批不是需求范围，不设计。操作后乐观移除该行；若返回 `ROOM_FULL`、`MEMBER_REQUEST_ALREADY_PROCESSED` 等错误则恢复该行并刷新状态。

### 5.9 内容审核 `/admin/reviews`

默认显示 `PENDING_REVIEW`，按提交时间、`roomSeq` 正序。顶部固定筛选：房间、发送者 ID、状态、提交时间；右侧是“批准所选”“拒绝所选”（选中 1–100 条才可用）。表格列：复选框、序号、内容（最多两行，点击看全文）、发送者、房间、提交时间、截止时间、状态、操作。

审核详情抽屉必须显示 `roomSeq` 及顺序说明。对批准后的 `APPROVED`，结果提示为：`审核已通过；该消息会在前序消息完成发布或跳过后自动发布。` 不显示“发布成功”。批量结果在提交后进入结果面板，按成功、已处理、无权限、未找到分组，允许部分成功；不得用“全部成功”的单一提示掩盖失败项。已被其他管理员或超时任务处理时，显示“此消息已被处理”，并刷新行状态。

### 5.10 广播与紧急通知 `/admin/publish`

页面分为两个页签：`管理员广播` 与 `紧急通知`，二者共享房间多选器和文本编辑区。房间多选器支持搜索、全选“我有权限的房间”，每个选项显示状态、人数和授权标识；已删除房间不可选。

- 管理员广播：主按钮“发送广播”。说明“广播不需要审核，但仍会按房间普通消息顺序发布；可能暂时等待前序消息。”
- 紧急通知：红色说明区写明“将立即置顶推送给所选房间成员，不受审核队列影响。”按钮为危险色“发送紧急通知”，必须二次确认并展示目标房间数。
- 文本计数与普通消息相同（0–320），不允许空白。提交后不关闭页面，而显示逐房间结果表：房间、发送结果、消息/通知序列、后续状态、失败原因。`PENDING_COMPENSATION` 显示“已保存，实时投递待补偿”，不可让管理员再次发送造成重复内容。

### 5.11 管理员授权、审计、取证与运行状态

**管理员授权。** 仅系统管理员。在房间详情的授权页中按“管理员用户 ID”添加授权；列表展示管理员 ID、授权人、授权时间及“撤销”。撤销需确认“将立即失去此房间管理与读取权限”。不设计角色提升功能。

**审计日志。** 系统管理员可查看全局审计；房间管理员只能在授权房间详情看到经过字段收敛的房间审计。筛选包括操作者、房间、消息、行为类型、时间；表格包含发生时间、操作者、行为、资源、状态前后变化、请求 ID。`detail` 仅在系统管理员详情抽屉展示。日志无编辑、删除、导出按钮。

**删除房间取证。** 仅系统管理员，入口放在审计页的“取证查询”，不是常规房间列表。必须先勾选“我确认这是只读取证查询，访问将记录审计”，再显式开启 `includeDeleted=true`。结果页使用红灰色只读横幅，并分区展示房间快照、成员、消息和审计；无恢复、编辑、订阅或发送按钮。

**运行状态。** 仅系统管理员，使用 2 × 4 指标卡：连接数、待审核数、今日审核超时、今日消息量、平均审核耗时、今日推送失败、HTTP 错误率、数据库连接池（活跃/空闲/上限）。顶部可切换 `当前` / `今日`，显示数据观察时间和“刷新”按钮。健康状态不是管理员业务页面的阻塞条件：接口不可用时显示“指标暂不可用”，保留最后一次成功数据并标注过期时间。

## 6. 实时状态、错误与数据处理规则

### 6.1 前端状态模型

每个房间独立存储 `{ subscriptionStatus, lastMessageSeq, lastNotificationSeq, messageIds, notificationIds, gap }`。普通消息和紧急通知绝不可共用单一序列或同一列表；跨房间也不承诺顺序。

| 事件 | 界面响应 |
| --- | --- |
| `CHAT_MESSAGE` | 按 `messageId` 去重，按 `roomSeq` 排序插入普通流；若非当前房间，更新未读数。 |
| `REVIEW_STATUS` | 更新“我的消息状态”和我的消息列表；`PUBLISHED` 只更新状态，等待/合并对应 `CHAT_MESSAGE`，不创建第二气泡。 |
| `NOTIFICATION` | 以 `messageId` 去重，插入独立通知层；当前房间立即展开横幅。 |
| `ERROR: SESSION_REPLACED` / 4001 | 关闭自动重连，显示跨设备登录提示。 |
| `ERROR: ROOM_DELETED` | 移除该房间订阅、草稿和未读数，返回可访问页面。 |
| `ERROR: ROOM_ACCESS_DENIED` | 取消订阅并刷新我的成员关系；说明访问权限已变化。 |
| `SUBSCRIBED_WITH_GAP` | 保持订阅，从最早可得内容继续；显示留存缺口提示。 |

### 6.2 错误文案

| 错误码/情况 | 面向用户文案 | 后续动作 |
| --- | --- | --- |
| `SENSITIVE_CONTENT_REJECTED` | 消息未能提交，请调整表述后再试。 | 保留草稿；不提及敏感词。 |
| `TOO_MANY_REQUESTS` | 发送过于频繁，请稍后再试。 | 显示服务端 `Retry-After` 倒计时。 |
| `ROOM_FULL` | 房间人数已满，暂时无法加入。 | 刷新成员数。 |
| `ROOM_PAUSED` | 房间已暂停，暂时不能进行此操作。 | 禁用相关动作。 |
| `ROOM_CLOSED` | 房间已关闭，不能进行此操作。 | 禁用相关动作。 |
| `ROOM_DELETED` | 房间已删除，无法继续访问。 | 返回列表/我的消息。 |
| `REVIEW_ALREADY_PROCESSED` | 该消息刚刚已被处理。 | 刷新该条状态。 |
| `IDEMPOTENCY_KEY_REUSED` | 请求状态异常，请刷新页面后重试。 | 不自动重放；记录诊断信息。 |

所有写操作生成 UUID v4 `requestId`，双击、网络重试和刷新后的恢复必须复用同一“正在提交”请求的 ID；用户重新编辑后再发则生成新的 ID。普通接口错误以行内提示为主，权限/会话失效使用全局提示和路由处理。

## 7. 响应式、无障碍与验收

### 7.1 响应式断点

| 宽度 | 布局规则 |
| --- | --- |
| ≥ 1280px | 完整侧栏，房间列表双列，聊天三栏。 |
| 768–1279px | 主导航保留；聊天隐藏成员栏，房间列表单列或双列按空间调整。 |
| < 768px | 导航与聊天辅助栏进入抽屉；表格改卡片；底部输入区固定并避开安全区。 |

移动端紧急通知仍固定在聊天头部下方；对话框宽度为视口减 32px。所有核心操作（加入、发送、审核、批准/拒绝）在单手宽度下不依赖悬浮才能发现。

### 7.2 无障碍

- 文本与背景对比度至少 4.5:1；状态不能只靠颜色，必须有文字和图标/边框。
- 所有可交互控件可键盘访问，有明显焦点环；表格批量选择和审核按钮支持键盘操作。
- 新消息、审核状态和连接状态更新使用 `aria-live="polite"`；紧急通知使用 `aria-live="assertive"`，但同一通知只播报一次。
- 聊天列表有“跳至最新消息”快捷按钮；屏幕阅读器不会因自动滚动而丢失阅读位置。
- 表单错误与字段通过 `aria-describedby` 关联，禁止只用红色边框提示错误。

### 7.3 UI 验收清单

- [ ] 用户绝不会在公共聊天流看到他人的待审、拒绝、超时或已删除房间未发布消息。
- [ ] `APPROVED` 在任何用户界面都明确表示“等待按序发布”，而非“已发布”。
- [ ] 紧急通知独立显示和去重，不破坏普通消息的 `roomSeq` 顺序。
- [ ] 重连、补偿、重复推送、留存缺口和会话替换均有可理解的可视反馈。
- [ ] 房间暂停/关闭/删除时，按钮、输入框和跳转入口同时反映服务端允许的动作。
- [ ] 审核批量操作、广播和紧急通知都能展示逐项结果与部分失败。
- [ ] 删除房间取证具有明确只读、显式开启和审计提示，常规路径不可访问。
- [ ] 所有发送与管理文本输入都按 Unicode code point 预校验为 0–320，服务端错误仍能正确回显。

## 8. 建议的前端模块划分

```text
src/
├─ layouts/        AppShell、AdminLayout
├─ views/          auth、rooms、chat、my-messages、admin/*
├─ components/     RoomCard、ChatTimeline、NotificationBanner、MessageComposer、
│                  ReviewStatusPanel、FilterBar、BatchResultPanel、StatusTag
├─ stores/         auth、room、chat、admin、connection
├─ websocket/      client、protocol、replay、message-reducer
├─ api/            auth、rooms、messages、admin、metrics
└─ utils/          request-id、unicode-count、error-message、cursor-pagination
```

建议将协议状态处理集中在 `websocket/message-reducer`：所有 `CHAT_MESSAGE`、`REVIEW_STATUS`、`NOTIFICATION` 和订阅事件先归一化、去重和排序，再由页面消费。这样聊天页、我的消息和管理审核页不会各自实现一套互相矛盾的状态判断。

## 9. 待确认项与补充建议

本节记录当前需求与 API 契约尚未完全确定、但会影响 UI 可用性或研发实现的事项。它们不是既定功能；在产品确认前，前端应采用本节的临时降级方案，且不应自行假设服务端能力。

| 优先级 | 待确认项 | 当前契约情况与 UI 影响 | 建议补充 / 临时方案 |
| --- | --- | --- | --- |
| P0 | 可授权管理员的检索 | `PUT /admin/rooms/{roomId}/authorizations/{adminUserId}` 只能按用户 ID 授权，未提供可搜索 `ROOM_ADMIN` 用户的接口。手动输入 ID 容易出错，无法完成易用的授权选择器。 | 增加仅系统管理员可用的管理员搜索接口（建议可按用户 ID、用户名、显示名查询）。接口补齐前，授权页使用带格式校验的“管理员用户 ID”输入框，并明确提示“请输入具备 ROOM_ADMIN 角色的用户 ID”。 |
| P0 | 管理工作台待办总数 | 审核和入群申请均为游标分页，契约未保证返回总数；前端不能从首屏列表准确得到“待审核 / 待审批”数量。 | 增加聚合待办接口，返回授权范围内的待审批数、待审核数、超时数与观察时间；或在分页信封中明确提供可信 `total`。补齐前，工作台只写“最新待处理项目”，不展示可能不准确的总量。 |
| P1 | 紧急通知未读状态 | 已提供通知历史和实时通知，但没有“已读 / 未读”记录、跨设备同步或清空规则。 | 产品需明确是否需要持久化未读。若不做，界面标注为“本次会话的新通知”，关闭横幅只在当前设备本地生效；不可展示跨设备未读红点。 |
| P1 | 取证数据的嵌套分页 | 取证接口返回成员、消息、审计三个分页区块，但各区块游标字段和继续加载请求参数需要进一步固化。 | 在接口响应中分别声明 `membersPage`、`messagesPage`、`auditPage` 的 `items`、`nextCursor` 与对应请求参数。补齐前，取证页仅实现首屏只读展示，不承诺“加载更多”。 |
| P1 | 时间与时区展示 | API 使用 RFC 3339 时间，但没有产品级的客户端展示时区规则。审计、审核截止与消息时间可能因设备时区不同而产生理解偏差。 | 统一约定服务端以 UTC 保存和传输，前端按浏览器本地时区显示；审计日志、取证和审核截止时间额外标注时区（例如 `2026-09-06 18:30 GMT+8`）。 |
| P2 | 账户设置范围 | 已定义注册、登录、刷新、退出和当前用户查询，未定义修改显示名、修改密码、找回密码或账号注销。 | 若本期不做，应在范围说明中显式排除，并且账号菜单不出现无法操作的入口。若需要，应新增相应接口、身份校验与审计规则。 |
| P2 | 交付物颗粒度 | 本文覆盖规范、逐页设计与关键聊天线框；但尚不是可直接像素对齐开发的高保真稿。 | 研发交接前补充：全部页面低保真线框、关键路径高保真稿、组件的默认/悬停/禁用/加载/错误状态，以及 API 字段到界面字段的映射表。 |

### 9.1 实施顺序

1. **先确认 P0**：管理员授权检索和待办总数会改变页面控件与数据源，确认后再实现管理工作台和授权页。
2. **再确认 P1**：通知未读、取证分页、时区规则会影响状态存储、文案和分页协议。
3. **P2 作为范围与交付质量控制**：不纳入本期的账户能力需从导航中移除；视觉稿和组件状态稿应在开发联调前完成。

普通成员仅展示 `ACTIVE` 成员的显示名和加入时间。紧急通知按 `notificationSeq` 的时间方向分页，不能插入普通聊天消息流；关闭通知抽屉不改变服务端消息或已读状态。


首屏加载使用页面骨架；“加载更多”失败只在列表底部显示可重试状态，不能覆盖已加载数据。权限失效、房间删除和会话替换属于页面级状态，应停止相关请求/订阅并提供唯一清晰的离开路径。

### 10.4 线框图验收补充

- [ ] 房间详情在 `OPEN`、`APPROVAL`、满员、暂停、关闭和已加入状态下都有明确且不冲突的主动作。
- [ ] 通知抽屉和成员抽屉的内容权限、分页方向与关闭行为已分别定义。
- [ ] 会话替换、房间删除、补偿缺口、暂停和关闭均有独立线框及可恢复/不可恢复提示。
- [ ] 管理员的新建、状态迁移、删除、审核详情、批量部分失败和紧急通知确认都具备确认或结果反馈界面。
- [ ] 空、加载、分页失败和权限失效不会被误表现为“无数据”。
