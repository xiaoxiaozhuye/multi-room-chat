# 多聊天室群聊业务规则与状态机（规范基线）

> 版本：1.0  
> 状态：已确认，供 REST、WebSocket、数据库及前端共同实现。  
> 规范优先级：本文件是聊天室生命周期、消息顺序、删除后访问、内容审核和 WebSocket 会话的唯一行为基线；与其他设计文件的描述不一致时，以本文件为准。

## 1. 术语与通用判定

| 术语 | 定义 |
| --- | --- |
| 有效成员 | `user_chat_rooms.status = ACTIVE` 的用户。`PENDING`、`REJECTED`、`EXITED` 均不是有效成员。 |
| 授权管理员 | 对目标房间有授权的 `ROOM_ADMIN`，或任意房间均有授权的 `SYSTEM_ADMIN`。管理员发送管理消息不要求其同时是有效成员。 |
| 普通消息 | `CHAT`（普通用户）和 `ADMIN_MESSAGE`（授权管理员）的合称；两者均属于普通消息通道。 |
| 紧急通知 | `SYSTEM_NOTIFICATION`；独立于普通消息通道的高优先级通知。 |
| 已删除房间 | `deleted_at IS NOT NULL`（或等价的 `deleted = true`）。它是对 `ACTIVE`、`PAUSED`、`CLOSED` 的终态覆盖，不能再对外作为可运营房间使用。 |
| 可查历史 | 仅返回已发布的普通消息和已发布的紧急通知；审核中的消息及他人被拒绝/超时的消息不在公共历史中。 |

所有权限判定均由服务端根据 JWT 身份、数据库中的房间删除标记、房间状态、成员关系和管理员授权完成；客户端传入的 `userId`、角色或授权范围均不得作为判定依据。

## 2. 聊天室业务规则矩阵

### 2.1 运营操作与房间状态

“允许”仍须通过身份、成员资格或管理员授权校验；“拒绝”表示请求不创建消息、不创建成员关系，也不产生普通业务审计记录（可产生安全拒绝日志）。

| 房间对外状态 | 用户加入/申请加入 | 普通用户 `CHAT` | 管理员普通消息 `ADMIN_MESSAGE` | 紧急通知 `SYSTEM_NOTIFICATION` | 房间公共历史查询与补发 |
| --- | --- | --- | --- | --- | --- |
| `ACTIVE` | 允许；`OPEN` 直接成为成员，`APPROVAL` 创建申请 | 允许；仅有效成员，进入审核 | 允许；仅授权管理员，直接进入普通消息发布序列 | 允许；仅授权管理员，立即发布 | 允许；有效成员及授权管理员可查/补发 |
| `PAUSED` | 拒绝 | 拒绝 | 允许；仅授权管理员 | 允许；仅授权管理员 | 允许；有效成员及授权管理员可查/补发 |
| `CLOSED` | 拒绝 | 拒绝 | 允许；仅授权管理员，用于收尾或说明 | 允许；仅授权管理员 | 允许；有效成员及授权管理员可查/补发 |
| 已删除 | 拒绝 | 拒绝 | 拒绝 | 拒绝 | 对外拒绝；仅系统管理员可走取证只读接口查询，见第 5 节 |

补充规则：

- `PAUSED` 是“冻结成员互动、保留管理员运营通知”的状态；`CLOSED` 是“停止用户运营、保留管理员收尾通知和历史”的状态。两者均不允许普通用户发言或新成员进入。
- 管理员广播到多个房间时，逐房间按本矩阵独立校验。返回逐房间结果；`PAUSED`、`CLOSED` 可接受管理员普通消息和紧急通知，已删除房间必须返回 `ROOM_DELETED`。
- 房间从 `ACTIVE` 变更为 `PAUSED` 或 `CLOSED` 后，已进入审核的 `CHAT` 不撤销；它们继续按既有审核截止时间完成审核、拒绝或超时，并按第 3 节的序列规则处理。状态变更之后不得再接收新的 `CHAT`。
- 删除房间时，全部尚未发布的 `CHAT` 必须在同一事务中从 `PENDING_REVIEW` 或 `APPROVED` 变为 `CANCELLED_BY_ROOM_DELETION`；不得再发布。该终态用于保留审计事实，且不会出现在公共或个人的“已发布”历史中。

### 2.2 历史数据的角色矩阵（未删除房间）

| 数据与接口类别 | 有效成员 | 授权管理员 | 系统管理员 |
| --- | --- | --- | --- |
| 房间公共历史、重连补发 | 可读已发布内容 | 可读已发布内容 | 可读已发布内容 |
| 本人消息及审核状态 | 可读本人所有状态（在消息留存期内） | 可读本人所有状态 | 可读本人所有状态 |
| 房间审核队列、被拒绝/超时内容 | 不可读他人数据 | 可读授权房间 | 可读全部房间 |
| 房间成员名单及成员状态 | 可读当前成员展示字段 | 可读授权房间的完整成员记录 | 可读全部 |
| 审计日志 | 不可读 | 可读授权房间相关审计，且仅限业务必要字段 | 可读全部审计 |

管理员权限在每次查询时重新检查；被撤销授权的 `ROOM_ADMIN` 立即失去上述管理员读取能力。

### 2.3 聊天室与成员状态机

聊天室创建后初始状态为 `ACTIVE`，不存在对外可用的草稿状态。`CLOSED` 与“已删除”均不可恢复；本期不提供恢复接口。

```text
                    暂停
              +--------------+
              |              v
创建 ------> ACTIVE <----> PAUSED
              |               |
              | 关闭          | 关闭
              v               v
                    CLOSED

ACTIVE / PAUSED / CLOSED --逻辑删除--> DELETED（终态）
```

| 当前状态 | 可执行的状态迁移 | 不允许的迁移 |
| --- | --- | --- |
| `ACTIVE` | `PAUSED`、`CLOSED`、`DELETED` | 无直接恢复外部已删除房间的路径 |
| `PAUSED` | `ACTIVE`、`CLOSED`、`DELETED` | 不可从暂停直接变为已删除以外的其他未列状态 |
| `CLOSED` | `DELETED` | 不可重新 `ACTIVE` 或 `PAUSED` |
| `DELETED` | 无 | 所有状态迁移和业务写入均拒绝 |

成员关系每次加入/申请都创建新记录，因此 `REJECTED` 与 `EXITED` 是该条成员记录的终态；用户重新申请时创建另一条记录。数据库约束同一 `(user_id, room_id)` 最多一条 `PENDING` 或 `ACTIVE` 记录。

```text
OPEN：       NONE --加入--> ACTIVE --退出--> EXITED
APPROVAL：   NONE --申请--> PENDING --批准--> ACTIVE --退出--> EXITED
                                  \--拒绝--> REJECTED
```

房间变为 `PAUSED`、`CLOSED` 或 `DELETED` 不改变既有成员记录状态；成员资格保留用于历史访问和取证，但 `DELETED` 的所有订阅和对外房间访问仍受第 5 节限制。

## 3. 消息顺序、优先级与消息状态机

### 3.1 序列的定义与发布门槛

1. 每个房间对所有普通消息维护唯一、单调递增、无复用的 `room_seq`。`CHAT` 和 `ADMIN_MESSAGE` 在同一数据库事务内分配该序列，因此**管理员普通消息与普通用户消息共同严格遵守 `room_seq` 顺序**。
2. 严格顺序的依据是服务端成功持久化时分配的 `room_seq`，不是客户端时间戳、到达 WebSocket 的先后或审核完成时间。
3. 普通消息只有在其之前每一个 `room_seq` 都已“发布”或已被终态跳过后，才能从 `APPROVED` 变为 `PUBLISHED` 并进入公共历史/推送。`REJECTED`、`TIMEOUT` 与 `CANCELLED_BY_ROOM_DELETION` 是可跳过终态。
4. `ADMIN_MESSAGE` 不需要人工审核，创建后即为 `APPROVED`，但**不可跨越更小 `room_seq` 的待审核普通用户消息**。因此管理员消息可能暂时等待审核超时或前序审核结果。
5. 数据库须保存每个房间的 `next_publish_seq`（或同等的可并发安全发布游标）。审核、超时、管理员提交和补偿任务均调用同一个“按序排空”事务/服务；不得由各自的 WebSocket 处理器直接越序推送。
6. 跨房间没有全局顺序保证。

### 3.2 紧急通知的旁路规则

- `SYSTEM_NOTIFICATION` 不占用、也不等待普通消息的 `room_seq`；其 `room_seq` 为 `NULL`。每个房间另有单调递增的 `notification_seq`，用于紧急通知去重、排序与断线恢复。
- 授权管理员提交紧急通知且房间未删除时，持久化和审计提交成功后即为 `PUBLISHED`，立即推送；不得等待任何 `PENDING_REVIEW` 或未发布的 `ADMIN_MESSAGE`。
- 客户端必须在单独的紧急通知通道立即置顶/显著展示；不得把紧急通知插入普通消息列表来破坏普通列表的 `room_seq` 单调展示。
- 重连订阅携带 `lastMessageSeq` 和 `lastNotificationSeq`。服务端分别补发 `room_seq > lastMessageSeq` 的已发布普通消息与 `notification_seq > lastNotificationSeq` 的紧急通知。客户端以 `messageId` 去重。

### 3.3 消息状态机

```text
普通用户 CHAT
  接收并通过基础校验
       |
       v
PENDING_REVIEW --管理员批准--> APPROVED --轮到 next_publish_seq--> PUBLISHED
       |                            ^
       |                            | 管理员普通消息创建时直接进入
       +--管理员拒绝--> REJECTED    |
       +--到达审核截止--> TIMEOUT   |
       +--房间逻辑删除--> CANCELLED_BY_ROOM_DELETION

紧急通知 SYSTEM_NOTIFICATION
  接收并通过授权/房间校验 --> PUBLISHED
```

| 状态 | 含义 | 是否公共可见 | 是否可再变更 |
| --- | --- | --- | --- |
| `PENDING_REVIEW` | 已持久化、等待审核 | 否 | 可到 `APPROVED`、`REJECTED`、`TIMEOUT` 或 `CANCELLED_BY_ROOM_DELETION` |
| `APPROVED` | 审核通过或管理员普通消息已就绪，等待其顺序发布 | 否 | 仅可到 `PUBLISHED`；房间删除时可到 `CANCELLED_BY_ROOM_DELETION` |
| `PUBLISHED` | 已纳入公共可见历史并已投递至推送补偿机制 | 是 | 不可变更 |
| `REJECTED` | 被管理员拒绝 | 否 | 不可变更 |
| `TIMEOUT` | 审核截止前未处理 | 否 | 不可变更 |
| `CANCELLED_BY_ROOM_DELETION` | 删除房间时被终止，保留审计证据 | 否 | 不可变更 |

审核批准、拒绝或超时均使用条件更新（例如 `WHERE status = 'PENDING_REVIEW' AND version = ?`）；只有一个竞争者成功。状态变化、对应审计日志和必要的房间发布游标更新必须在同一个 PostgreSQL 事务中完成。WebSocket 是至少一次投递：投递失败只创建/保留补偿工作，不回滚 `PUBLISHED`，客户端必须用 `messageId` 幂等展示。

## 4. 配置与输入边界

### 4.1 敏感词

- 权威来源为部署时注入的外部化应用配置：`chat.moderation.sensitive-words`（词项）与 `chat.moderation.match-mode`（匹配规则）。本期不提供敏感词 REST 管理接口，也不以 Redis 或消息表作为词库来源。
- 运维通过受版本控制的配置文件、环境变量或密钥配置系统更新该配置；变更经发布/滚动重启后生效。服务启动时校验并编译词库，Redis 仅可缓存编译结果，失效后必须从外部化配置重建。
- 服务端在创建 `CHAT` 前执行检测。命中时返回统一业务错误 `SENSITIVE_CONTENT_REJECTED`，不入 `messages`、不进入审核超时索引，且不向客户端透露命中的词项或规则。`ADMIN_MESSAGE` 与 `SYSTEM_NOTIFICATION` 不经敏感词自动拦截，但均需授权且必须审计。

### 4.2 审核超时

- 配置键为 `chat.review.timeout-seconds`，默认值为 **30 秒**。
- 接收 `CHAT` 时计算并持久化 `review_deadline_at = created_at + 当前配置值`，Redis ZSet 只是该截止时间的调度索引。之后修改配置不追溯改变已提交消息的截止时间。
- 到期任务以数据库条件更新完成 `PENDING_REVIEW → TIMEOUT`；Redis 丢失或重建不会改变以 `review_deadline_at` 为准的结果。

### 4.3 文本长度和 Unicode

- 仅接受有效 Unicode 标量值组成的文本。空字符串或去除首尾空白后为空的文本被拒绝。
- “最多 320 个 Unicode 字符”精确定义为 **最多 320 个 Unicode code point（Unicode 标量值）**，不按 UTF-8 字节数、UTF-16 `char` 数或用户感知的字形簇计数。
- 服务端以 Java `String.codePointCount(0, value.length())` 计数；存在未配对 UTF-16 代理项的输入必须拒绝。前端使用 `Array.from(text).length` 进行同口径预校验，但服务端校验是最终依据。
- 不做 Unicode 归一化后再计数；组合字符按各自 code point 分别计数。例如一个表情符号通常计 1，`e` 加组合重音计 2，一个家庭 ZWJ 表情会计多个 code point。

### 4.4 留存期限

| 数据 | 保留规则 | 到期处理 |
| --- | --- | --- |
| 普通消息与紧急通知正文 | 自 `created_at` 起 3 个月 | 按既有归档/清理任务处理；不再出现在在线历史或补发中 |
| 成员关系 | 保留至房间逻辑删除后的取证数据清理策略执行；本期不因用户退出而删除 | 状态记录保留，避免丢失加入/退出事实 |
| 审计日志 | 自 `created_at` 起 **3 年** | 到期后由受控的留存任务清理；清理任务自身必须产生系统级审计事件 |

审计日志在保留期内不可由业务接口修改或删除。上述期限是本系统的产品默认值，不替代适用法律、合同或监管要求；若适用要求更长，部署配置与留存任务必须取较长者。

#### 4.4.1 消息正文清理策略

默认策略为**不可逆的正文清除**，而不是删除 `messages` 行或移动到另一张归档表：到期且已处于
`PUBLISHED`、`REJECTED`、`TIMEOUT` 或 `CANCELLED_BY_ROOM_DELETION` 终态的消息，在固定批次截止点
`created_at < cutoff_at` 被置为 `content=NULL`，并写入 `content_retired_at`。消息 ID、发送者、房间、
序列、类型、状态、时间戳和版本仍保留；因此聊天室、成员关系、发布游标、审计日志的 `message_id`
外键和取证筛选都不会被破坏。未终态消息不属于候选集，必须先由审核/超时流程结束，避免清理任务影响审核。

在线公共历史、本人历史和常规管理消息列表均不返回已清除消息正文，也不以占位文本伪造原内容。管理员
取证和审计查询仍可按 `messageId`、`roomId` 查询到关联元数据及 `MESSAGE_CONTENT_PURGED` 审计事件，但
正文不可恢复。重连补偿跳过已清除正文；只要请求序列范围内存在该类缺口，订阅响应为
`SUBSCRIBED_WITH_GAP`，相应通道的 `*ReplayStatus=GAP`，并返回最早仍可补偿的序列。值为 `"0"`
表示该通道已经没有任何可补偿正文，客户端必须提示“超出留存期”，不得将其作为网络失败重试。

#### 4.4.2 清理运行、重试和人工保护

消息清理默认每天 03:20 UTC 运行，按最多 500 条/批使用 `FOR UPDATE SKIP LOCKED` 取得候选行；多实例
或人工运行并发时只会由一个事务取得同一行。每次写入还带有 `content_retired_at IS NULL`、终态和固定
截止点条件，因此重试和重复运行均是幂等的，绝不会清除运行开始后才到期的数据。单批数据库或审计写入
失败会整体回滚，并至多立即重试 3 次；最终失败写为 `FAILED`，下一次调度可安全继续。

每次运行在 `message_retention_runs` 中记录触发来源、操作者（人工时）、截止点、批次数、清除数、重试数、
错误摘要、开始/结束时间，并产生 `MESSAGE_RETENTION_RUN` 审计；每条实际清除消息产生
`MESSAGE_CONTENT_PURGED` 审计。人工触发仅允许 `SYSTEM_ADMIN` 调用
`POST /api/v1/admin/retention/messages/purge`，且请求体必须显式包含
`{"confirmation":"PURGE_EXPIRED_MESSAGE_BODIES"}`。审计日志不由该任务选择或删除；其 3 年独立留存
策略必须由独立、受控的审计留存流程执行。

## 5. 逻辑删除房间后的数据访问规则

删除在一个数据库事务中完成：写入 `deleted_at`/`deleted_by`、记录 `ROOM_DELETE` 审计、取消未发布普通消息，并使该房间所有实时订阅失效。删除不物理级联删除消息、成员关系或审计日志。

| 访问主体 | 房间详情/列表 | 公共历史、WebSocket 订阅/补发 | 本人消息记录 | 成员记录 | 审计日志与全部消息取证 |
| --- | --- | --- | --- | --- | --- |
| 普通用户（含原成员） | 不返回（`ROOM_DELETED`） | 拒绝 | 可在“我的消息”中读取本人消息至消息留存期；返回 `roomDeleted=true`，不提供房间公共入口 | 不可读 | 不可读 |
| 原授权 `ROOM_ADMIN` | 不返回 | 拒绝 | 同普通用户 | 不可读 | 不可读 |
| `SYSTEM_ADMIN` | 常规列表默认不返回；仅 `includeDeleted=true` 的管理取证接口可读 | 常规订阅/补发拒绝 | 可按授权的管理查询读取 | 仅取证只读接口可读 | 可在取证只读接口读取，至各自留存期 |

删除后的任何读取均不得恢复房间可见性、成员资格或订阅资格；本期不提供“恢复已删除聊天室”接口。所有取证接口必须显式要求 `includeDeleted=true`、记录读取审计，并默认分页；不能通过普通用户接口或普通管理员接口旁路访问。

## 6. WebSocket 单用户单连接状态机

策略确定为：**新连接替换旧连接（last connection wins）**，而不是拒绝新连接。

```text
NEW --JWT 校验失败--> REJECTED
NEW --JWT 校验成功--> REGISTERING
REGISTERING --无旧会话--> ACTIVE
REGISTERING --存在旧会话--> REPLACING --向旧会话发 SESSION_REPLACED 并关闭(4001)--> ACTIVE
ACTIVE --心跳超时/网络关闭/主动关闭--> CLOSED
ACTIVE --同用户新连接--> REPLACED --> CLOSED
```

实现要求：

1. 会话注册按 `userId` 原子替换，并给每个会话分配唯一 `sessionId` 或递增 `generation`。新会话注册成功后才关闭旧会话。
2. 旧会话收到关闭回调时，只有其 `sessionId` 仍是该用户当前映射时才能清除映射、在线状态和订阅；不得因旧会话回调误删新会话。
3. 被替换的旧连接先收到业务事件 `SESSION_REPLACED`（尽力而为），随后以应用关闭码 `4001` 关闭；客户端收到该事件或关闭码应停止旧连接重连循环。新连接可立即订阅并按双游标补偿。
4. 一条连接可以订阅多个房间；每次订阅和每次发送都重新校验第 2 节的权限。房间删除、成员退出或授权撤销时，服务端立即取消受影响订阅并发送相应错误/状态事件。

## 7. 边界场景决策记录

| 编号 | 场景 | 决策与原因 |
| --- | --- | --- |
| BR-01 | `room_seq=10` 的用户消息待审，`room_seq=11` 的管理员普通消息已提交 | 11 保持 `APPROVED`，等待 10 审核通过后依序发布，或 10 拒绝/超时后跳过。保证一个普通消息流严格有序。 |
| BR-02 | 同一时刻发送紧急通知 | 紧急通知不分配 `room_seq`，立即 `PUBLISHED` 并以 `notification_seq` 推送；它可以先于 10、11 展示，但不改变普通消息列表顺序。 |
| BR-03 | 房间暂停/关闭时有待审消息 | 不撤销已接收消息；按既有截止时间审核和顺序排空。状态只阻止之后的新 `CHAT`。 |
| BR-04 | 房间删除时有待审或已批准未发布消息 | 原子标记为 `CANCELLED_BY_ROOM_DELETION` 并写审计；禁止补偿发布，防止删除后重新出现内容。 |
| BR-05 | 管理员审核与超时任务并发 | 以带版本/状态的条件更新竞争；仅一个成功，失败方返回/记录“已处理”，不会重复审计或重复推进发布游标。 |
| BR-06 | 已删除房间的原成员请求历史或重连 | 房间历史与订阅一律 `ROOM_DELETED`；“我的消息”仅能查自己的留存数据，且标注房间已删除。 |
| BR-07 | 敏感词命中或限流 | 在消息持久化前拒绝；不占 `room_seq`、不写审核队列，避免制造永久顺序空洞。 |
| BR-08 | 修改审核超时配置 | 仅影响修改后接收的消息；已有消息以持久化的 `review_deadline_at` 为准，防止同一消息的截止时间漂移。 |
| BR-09 | 用户在两台设备同时连接 | 第二条认证成功的连接成为唯一活动会话，第一条被 4001 关闭；所有旧会话清理均做 `sessionId` 比较。 |
| BR-10 | 长度含表情、组合字符或 UTF-16 代理项 | 以 code point 计数；有效的补充平面字符计 1，组合序列按多个 code point 计，未配对代理项拒绝。 |

## 8. 实现对照清单

| 层 | 必须遵守的规则 |
| --- | --- |
| REST | 写操作返回精确拒绝原因（如 `ROOM_PAUSED`、`ROOM_CLOSED`、`ROOM_DELETED`）；历史接口区分公共、本人、审核与取证读取范围。 |
| WebSocket | 普通消息和紧急通知使用独立序列/双游标；实现替换旧会话、关闭码 4001、订阅即时撤销与 `messageId` 去重。 |
| 数据库 | 房间保存删除时间与普通消息发布游标；消息支持 `notification_seq`、`review_deadline_at`、`CANCELLED_BY_ROOM_DELETION` 与并发版本；审计不可变。 |
| 前端 | 字数按 code point 预校验；普通流严格按 `room_seq` 展示；紧急通知独立置顶；收到删除或会话替换事件后清理订阅/停止旧连接。 |
